1Cloud Architecture Fundamentals

Cloud computing is on-demand access to shared compute, storage, networking, databases and higher-level services. Cloud architecture is the design of those capabilities around workload requirements for security, reliability, performance, scalability, operability and cost.

Regions

Geographic areas containing provider infrastructure. Select them using latency, sovereignty, service availability and resilience requirements.

Availability Zones

Separated infrastructure locations inside a region. Multi-zone designs reduce dependence on a single facility.

Control plane

APIs and management systems used to create and configure resources.

Data plane

The path through which application traffic and workload data actually flows.

Other foundations include edge locations, global resources, resource hierarchies, multi-tenancy, scalability, elasticity, resilience, fault tolerance and high availability. High availability is not the same as disaster recovery.

Example: A production web service can use a global DNS layer, CDN/WAF, a load balancer, stateless application instances across zones, a replicated database and centralized observability.

2Traditional / Native Systems vs Cloud

Traditional environment

Internet ↓ Firewall ↓ Load Balancer ↓ Web Servers ↓ Application Servers ↓ Database ↓ SAN / NAS Storage

On-premises environments commonly include physical servers, VMware ESXi and vCenter, SAN/NAS, switching, firewalls, load balancers, backup platforms and a DR site. Procurement and capacity planning happen before the workload needs the capacity.

Cloud equivalent

Internet ↓ DNS / CDN / WAF ↓ Managed Load Balancer ↓ Auto-scaled Compute / Containers ↓ Managed Database ↓ Object / Block / File Storage
Area Traditional Cloud
Hardware Owned or leased and lifecycle-managed Provider-owned infrastructure exposed as services
Provisioning Procure, rack, configure, install API, console or IaC
Scaling Capacity often purchased ahead Can be automated, subject to limits and cost
DR Often second site and replication Zones, regions, backups and managed replication
Operations Hardware, hypervisor, storage and network More provider-managed layers, but customer security/configuration remain
Trade-off: Cloud changes the abstraction boundary; it does not eliminate infrastructure responsibility.

3Why Companies Are Moving to Cloud

Cloud adoption is driven by speed, elasticity, global reach, managed services, automation, DevOps, CI/CD, IaC, analytics, AI/ML and reduced hardware lifecycle work.

Faster provisioning

Resources can be created through APIs and pipelines.

Elastic capacity

Workloads can add or remove capacity when demand changes.

Managed services

Teams can consume databases, queues and identity without operating every layer.

Global delivery

Applications can be deployed near users and across failure domains.

Why not move everything? Cost unpredictability, vendor lock-in, data residency, compliance, latency, legacy dependencies, licensing, migration complexity, skills gaps, security responsibility and egress costs can justify retaining or hybridizing workloads.

5Cloud Architecture Core Concepts

Scalability

Ability to handle increased workload by adding capacity.

Elasticity

Dynamic adjustment of capacity as demand changes.

Resilience

Ability to continue or recover when components fail.

Statelessness

Durable state is externalized so requests can move between instances.

Horizontal scaling adds instances; vertical scaling increases instance capacity. Load balancing distributes traffic. Caching reduces repeated reads. Queues decouple producers and consumers. Event-driven systems react to events. Monoliths can be simpler; microservices provide independent scaling/deployment at the cost of distributed-system complexity. Serverless reduces infrastructure operations but has service-specific limits.

11Cloud Security

The Shared Responsibility Model changes with the service model. Customers remain responsible for identity, configuration, data protection and workload security even when the provider manages the underlying infrastructure.

Identity

Least privilege, MFA, roles, workload identities and access review.

Data

Encryption at rest/in transit, key management, backups and classification.

Network

Segmentation, private subnets, controlled ingress/egress and WAF.

Operations

Audit logs, vulnerability management, security findings and incident response.

14Kubernetes & Cloud-Native Architecture

Users → Cloud LB / Ingress → Services → Pods → Persistent Volumes → Managed Cloud Data Services

EKS, AKS and GKE provide managed Kubernetes control planes. Production architecture still requires node capacity planning, workload identity, networking, ingress, storage, autoscaling, observability, secrets, upgrades, security and multi-cluster governance.

15Infrastructure as Code

Terraform is multi-cloud; CloudFormation/CDK are AWS-oriented; Bicep is Azure-oriented. IaC should be versioned, reviewed and deployed through controlled pipelines.

Git → Pull Request → Validate / Scan → Plan → Review → Apply → Cloud
resource "aws_s3_bucket" "example" {
  bucket = "example-production-bucket"
}

output "bucket_name" {
  value = aws_s3_bucket.example.bucket
}

Production concerns include remote state, locking where supported, modules, drift, secrets, state protection and CI/CD integration.

16Cloud CI/CD & DevOps

Developer → Git → CI → Test → Security Scan → Registry → IaC/Deploy → Kubernetes/Serverless/VM → Monitoring

Jenkins, GitHub Actions, GitLab CI, AWS CodePipeline, Azure DevOps and Cloud Build can implement delivery pipelines. ArgoCD supports GitOps for Kubernetes.

Best practice: Build immutable artifacts, scan dependencies/images, separate build from deployment, use environment promotion and keep deployment credentials out of source code.

18High Availability & Disaster Recovery

Pattern Purpose
Single AZ Simple but vulnerable to zone failure.
Multi-AZ Reduces dependence on one zone.
Multi-region Protects against regional failure at higher complexity/cost.
Active-passive Standby takes traffic after failover.
Active-active Multiple sites serve traffic concurrently.

RPO is acceptable data loss measured in time. RTO is target restoration time. Backups, snapshots and replication solve different failure modes and must be tested.

19Cloud Cost Optimization

  • Right-size compute and databases.
  • Remove idle resources.
  • Use autoscaling for variable workloads.
  • Use commitments when utilization is predictable.
  • Use spot/preemptible capacity for interruptible jobs.
  • Apply storage and log-retention policies.
  • Monitor network transfer and egress.
  • Tag resources and assign cost ownership.
  • Use budgets and anomaly alerts.
Cloud is not automatically cheaper. Stable workloads may favor owned infrastructure while bursty workloads may benefit from elasticity.

20Real-World Cloud Architectures

Three-tier web

DNS/CDN/WAF → load balancer → stateless web/app tier → managed database.

Microservices

API gateway → services → queues/events → service data stores. Requires tracing, timeouts and idempotency.

E-commerce

Global edge → web → catalog/order → cache → database → events/payment integrations.

Hybrid VMware + Cloud

On-prem VMware connected by private connectivity or VPN to cloud networks for phased migration and integration.

DR

Primary region → backup/replication → secondary region → tested failover.

Multi-cloud

Global traffic layer → provider-specific stacks → carefully designed data strategy. Use only when there is a clear reason.

For every architecture ask: what happens when an instance, zone, database, dependency or network path fails? How is it detected, recovered, secured, monitored and paid for?

21Cloud Migration Strategy

Assess → Discover → Plan → Design → Migrate → Validate → Optimize
Strategy Meaning
Rehost Move with minimal application changes.
Replatform Move while adopting selected managed capabilities.
Refactor Redesign internals for cloud-native operation.
Repurchase Replace with another product/service.
Retain Keep where it is when migration is not justified.
Retire Remove workloads that no longer provide value.

For VMware-to-cloud migration: inventory VMs and dependencies, classify workloads, map networks/identity, assess licensing and performance, pilot, validate, migrate in waves, then optimize.

22Cloud Architecture Interview Preparation

Q: What is scalability vs elasticity?

Answer: Scalability is the ability to handle more load; elasticity emphasizes dynamically adjusting capacity as demand changes.

Q: What is an Availability Zone?

Answer: A physically separated infrastructure location inside a cloud region.

Q: What is shared responsibility?

Answer: The provider secures the cloud infrastructure while customer responsibilities depend on the service and include configuration, identity and data/workload security.

Q: What is RPO?

Answer: Maximum acceptable data loss measured in time.

Q: What is RTO?

Answer: Target time to restore service.

Q: Why use a queue?

Answer: To decouple producers and consumers, absorb bursts and enable asynchronous processing.

Q: Why can cloud cost more?

Answer: Idle resources, overprovisioning, egress, service premiums and weak governance can raise total cost.

Q: What is GitOps?

Answer: A delivery approach where version-controlled desired state drives automated reconciliation.

Q: Object vs block storage?

Answer: Object storage is API/object based; block storage presents volumes suitable for filesystems and VM disks.

Q: Why private subnets?

Answer: To reduce direct internet exposure for resources that do not need public inbound connectivity.

For architecture interviews, explain requirements, trade-offs, failure modes, security, operations and cost—not just service names.
